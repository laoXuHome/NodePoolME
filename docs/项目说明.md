# NodePoolME 项目说明

> 当前版本：**v1.7.4**
> 更新日期：2026-11-25  
> 项目地址：<https://github.com/laoXuHome/NodePoolME>

## 1. 项目定位

NodePoolME 是一个自包含的多机场缓存池管理与统一订阅系统。它把多个机场订阅汇聚到一个本地缓存池，经过统一检测、筛选和重命名后，只对外提供一个订阅地址 `/sub/all`。

适合个人或小团队自建使用，不依赖 Subs-Check-Pro、Sub-Store 或任何第三方订阅转换服务。一个 Docker 容器即可运行，业务数据存放在 SQLite，前端静态页面由后端直接托管。

核心目标：

- 多个机场，一个订阅出口。
- 拉取、检测、输出三段解耦，互不阻塞。
- 检测只看本地缓存，不会因为检测而重新拉取机场。
- 只有通过双目标延迟门槛的节点才会下发。
- 订阅文件原子替换，失败不会破坏上一版。

## 2. 核心设计

### 2.1 三段式结构

```text
机场订阅 1..N
    ↓ 独立周期 / 手动 / 重试
订阅拉取器 → 下载 → 解析 → 校验 → 事务性写库
    ↓
SQLite 缓存池（全量缓存）
    ↓ 只读缓存
检测调度器 → 延迟检测 + 标签检测 + 并发限流 + 相似分散
    ↓
结果汇总 → 双目标门槛 → 动态命名 → 格式生成 → 原子替换
    ↓
/sub/all（Clash / sing-box / Base64）
```

三个环节只通过 SQLite 和订阅文件交换状态。检测过程中不会触发机场拉取；拉取失败也不会清空已有节点。

### 2.2 双目标延迟门槛

每个节点每一轮都要访问两个延迟探测地址：

- 目标 1：默认 Google，`http://www.google.com/favicon.ico`
- 目标 2：默认 Wikipedia，`http://www.wikipedia.org/favicon.ico`

两个地址的名称、链接、期望状态码、超时和各自延迟上限都可在系统设置中修改。

每个目标各测 **3 轮**，同一个节点严格按 `G → W → G → W → G → W` 轮询，不会连续访问同一个地址 3 次，也不会同时访问两个地址。

判定规则：

- 单个目标：3 轮中只要有 **任意一轮成功，且延迟不超过该目标自己的上限**，这个目标就算达标。
- 整个节点：目标 1 和目标 2 **都达标**才下发。
- 只有一边达标、另一边 3 轮全失败或全部超上限，节点不下发。
- 单节点同一时刻最多只有一个测试请求在途；标签检测与延迟检测共用同一把节点锁。
- 不同节点之间可以并行，受全局并发和网段并发限制。

### 2.3 标签只负责命名

节点标签（ChatGPT、Telegram、YouTube 及自定义组）的结果只决定节点名称中的标识段，**不参与是否下发的判定**。

例如：

```text
机场A·GPTᐧTGᐧYT·香港01
机场A·GPT·日本02
机场A·香港03
```

- `·` 是外层分隔符。
- `ᐧ` 是标签之间的分隔符。
- 命中哪些标签会随每轮结果动态变化。
- 原始节点名始终保留在最后一段。
- 未命中任何标签时，名称中不显示标签段。

### 2.4 下载测速（独立模块）

测速只反映节点真实下载能力，**不参与延迟门槛、可用性、评分和自动下发**，也不修改节点状态与失败次数。

```text
定时计划 / 手动 / 全部重测 / 新节点
              ↓
        统一测速队列（防重复 + 全局并发）
              ↓
   节点本地 SOCKS → 公共 HTTPS 测速源（多源、Range、4 连接）
              ↓
   单节点单轮累计流量上限（默认 50 MB）
              ↓
          MB/s → 五级速度标签
              ↓
 节点名最前段 / 缓存池速度列 / 下发等级排除
```

- 定时测速固定使用 `Asia/Shanghai`，默认 18:00—23:30；计划在窗口内均匀随机分散，窗口外不启动新任务，错过不补测。
- 执行频率由用户设为每天一次或每隔 N 天一次；不根据节点稳定性自动调整频率。
- 单节点单轮的所有测速源、连接和重试共享同一份流量额度，按实际收到的字节计数；达到上限立即停止，已取得的有效数据仍可按实际速度评级。
- 手动、全部重测、新节点重测不受时间窗口限制，全部进入同一队列；同一节点不会重复执行。
- 机场排除优先级最高：排除机场不建任务、不耗流量，节点名与速度列统一显示 `⚪`。
- 每次测速保留原始 run/sample；失败或异常不会覆盖之前的有效标签。最新有效结果默认保留 3 天，过期只显示待测速，不判故障、不自动补测。
- 订阅输出的「测速标签排除」为全局过滤：五级速度标签和待测速、已排除、异常、全源失败四种状态都可勾选，勾选即排除带该标签的节点；不再生成客户端独立筛选地址。

## 4. 首次使用流程

1. 部署容器，打开 Web 管理页，用 `NODEPOOL_ADMIN_PASSWORD` 登录。
2. 在「机场管理」添加机场，填写名称和订阅地址。
3. 设置拉取周期：
   - 只填间隔分钟数：按间隔拉取。
   - 只填每天时刻：每天定点拉取。
   - 两者都填：谁先到谁先拉。
   - 间隔填 `0` 且时刻留空：仅手动拉取。
4. 保存后点「立即拉取」，等待节点进入本地缓存池。
5. 在「节点标签」确认默认节点标签，按需新增自定义组。
6. 在「系统设置」配置两个延迟探测地址、各自延迟上限、检测超时等。
7. 在仪表盘点「立即检测并下发」，或等待自动批次。
8. 在「订阅输出」复制 `/sub/all` 地址到客户端。

## 5. 机场管理

### 5.1 拉取方式

每个机场独立配置：

- **间隔拉取**：按分钟周期执行。
- **每天定时**：每天固定时刻执行。
- **两者都设**：哪个时间先到就按哪个执行。
- **仅手动**：间隔为 `0` 且定时为空，系统不会自动拉取。

拉取动作不会因为检测批次而暂停，除非正在执行定时下发；定时下发期间会临时暂停拉取，避免缓存池在批次中途被改写。

### 5.2 失败保护

拉取流程是：下载 → 解析 → 校验 → 事务性写库。

以下情况都会保留旧缓存：

- 下载失败。
- 返回空内容。
- 解析失败。
- 数据校验不通过。

机场列表中会显示最近一次拉取的状态、错误原因、节点数量和拉取历史。

### 5.3 启停与缓存

停用机场后：

- 该机场的节点立即退出缓存池。
- 不计入统计。
- 不参与检测。
- 不进入 `/sub/all`。

重新启用时直接从本地缓存恢复，不会重新拉取订阅，并顺延下一次自动拉取时间。

### 5.4 按机场过滤节点

每个机场独立维护一组过滤关键词，默认是：

`官网`、`工单`、`客服`、`下载`、`失效`、`复制`、`客户端`、`如果`、`网站`、`剩余`、`套餐`、`重置`、`到期`、`流量`

规则：

- 原始节点名包含任一关键词（不区分大小写），整条不导入缓存池。
- 被过滤节点单独存放在 `airport_filtered_nodes`，**从不参与检测、从不进入 `/sub/all`**。
- 修改关键词后立即对现有缓存重新归类，不需要重新拉取；清空关键词表示该机场不过滤。
- 机场管理每个机场后面有「过滤」入口，可查看当前被过滤节点、编辑关键词、恢复默认。
- 「加入缓存池」会把某个被过滤节点手动放回缓存池，并记录为已准入；之后重新拉取时即使节点名仍命中关键词，也会继续保留，不会被再次过滤。
- 手动准入不是永久白名单：如果机场源里不再返回该节点，记录会随缓存一起清理。

## 6. 缓存池

### 6.1 节点保留

每个解析出的节点都单独写入缓存，不按协议、服务器、端口或参数合并。机场把同一配置写成多个不同名称时，这些条目会全部保留；缓存键会在重复内容上追加序号，确保同一条订阅里的 60 个条目不会因为内容相同而只剩 20 个。展示名称重复时，订阅生成阶段会自动追加 `#2`、`#3` 以保持 Clash / sing-box 名称唯一。

### 6.2 筛选

支持以下条件，多个条件按 AND 组合：

- 名称 / 服务器搜索
- 机场
- 协议
- 地区
- 可用状态
- 节点标签命中 / 未命中
- 标签（所选标签必须全部命中）
- 下载速度（优/良/中/差/危/待测速/已排除/异常/全源失败，可多选，结果为并集）
- 下发结果

标签筛选始终是正向 AND，不会因为同时选择「未命中所选组」而被反转。

### 6.3 延迟显示

缓存池的 `G / W` 列显示该目标最近 3 轮中**最低的实测延迟**，不管这一轮是否通过、是否超上限、是否最终下发。

- 超过该目标上限的数字会标红加粗。
- 即使节点「不下发」，延迟数值也会保留显示。
- 节点详情页保留每一轮原始延迟记录，包括失败轮次。
- 下发原因通过悬停或详情页查看，例如「Google 未通过（上限 500ms）」「缺少标签」。

### 6.4 手动测试

节点详情页支持三种模式：

- **只测延迟**：只跑两个延迟目标，不跑标签。
- **只测标签**：只跑启用的节点标签，不跑延迟。
- **全部测试**：延迟和标签都跑。

手动测试完成后，如果节点满足下发条件且当前已有订阅，会将该节点增量追加到订阅中，不重跑全局批次，也不覆盖其他节点。

## 7. 检测系统

### 7.1 默认节点标签

| 名称 | 标识 | 检测地址 | 成功条件 |
| --- | --- | --- | --- |
| ChatGPT | `G` | `https://chatgpt.com/` | 状态码 200–399 |
| Telegram | `TG` | `https://telegram.org/` | 状态码 200–399 |
| YouTube | `Y` | `https://www.youtube.com/generate_204` | 状态码 204 |

所有**启用**的节点标签在每个检测批次中都会运行。页面不再提供单个标签的「运行」按钮；标签只能随全局检测一起执行，避免单组运行覆盖其他标签结果。`间隔` 字段不再单独控制某个组是否到期，批次节奏由全局「检测批次间隔」或定时下发控制。

自定义节点标签支持：

- 名称（内部显示）
- 标识（进入节点名）
- 检测 URL
- HTTP 方法：GET / HEAD
- 预期状态码，支持 `200`、`200-399`、`200,204` 等写法
- 响应内容包含（可选）
- 最大延迟（可选）
- 排序值
- 启用 / 停用

检测超时是全局值，延迟探测和所有标签检测共用。

### 7.2 检测引擎

- **mihomo（默认）**：容器内启动 Mihomo 内核，为块内每个节点绑定独立回环 SOCKS 入口，发起真实 HTTP 请求，读取状态码、响应头和耗时。
- **tcp（降级）**：只验证 `server:port` 能否建立 TCP 连接，不校验状态码和响应体。内核不可用时自动降级，日志会标注。

Mihomo 支持的主要协议：

```text
ss / ssr / vmess / vless / trojan / hysteria / hysteria2
tuic / anytls / socks5 / http
```

其中 vmess 支持 h2、ws、grpc 等传输；vless 支持 REALITY。

### 7.3 调度与并发

- 节点按 200 个一块处理，每块重新绑定内核配置。
- 块内节点先随机打乱，再按同 IP / 同网段分桶并交错排列，避免相似节点连续请求。
- 单节点内部严格串行；节点之间并行。
- 四层并发限制：
  - 全局并发
  - 单节点标签并发
  - 同 IP 并发
  - 同网段并发
- 每次请求前加入随机间隔。

### 7.4 失败处理

- 单次失败不删除节点。
- 连续失败达到阈值后标记为 `unavailable`。
- 任意一次成功立即恢复 `available` 并清零失败计数。
- 错误分类包括：`timeout`、`connect`、`status`、`content`、`slow`、`engine`。
- 检测历史写入数据库，按保留天数自动清理。

## 8. 运行控制与进度

### 8.1 进度计算

批次总进度按「节点数 × 项目数」计算：

```text
每个节点 = 2 个延迟目标 + 启用的标签组数量
```

一个延迟目标虽然内部要跑 3 轮，但在进度条上仍只算 1 个项目，完成该目标的 3 轮后才推进一次。因此检测较轻时，进度条可能在某个数值停留较久，但节点仍在正常检测，不代表卡死。

### 8.2 暂停 / 继续 / 停止

- **暂停**：在当前请求的安全边界暂停，不再发起新请求；已发出的请求会自然结束。
- **继续**：恢复队列，继续处理剩余节点。
- **停止并下发**：停止后续节点，已完成的检测结果立即汇总，并按当前进度生成订阅；未完成的节点本次不参与。
- 停止不会改变定时下发的间隔计时，下一次仍按原计划执行。
- 停止后的批次状态记为 `stopped`，不会误判为失败。

## 9. 订阅输出

### 9.1 地址

唯一订阅入口：

```text
/sub/all?token=<订阅Token>
/sub/all/<订阅Token>
/sub/all/<订阅Token>/<format>
```

格式参数：

| 格式 | 参数 | 说明 |
| --- | --- | --- |
| Clash / Mihomo YAML | `format=clash` | `proxies` + 选择组 + 自动测速组 + `MATCH` |
| sing-box JSON | `format=singbox` | `mixed` 入站 + selector / urltest 出站 |
| 通用 Base64 | `format=base64` | 供 v2rayN 等客户端导入 |

不带格式参数时按 User-Agent 自动选择：

- 含 `sing-box`：sing-box JSON
- 含 `clash` / `mihomo` / `meta`：Clash YAML
- 其他：Base64

### 9.2 安全与发布

- 订阅 Token 可在「订阅输出」页修改或重新生成。
- 订阅内容不包含机场原始订阅 URL，也不包含机场凭据。
- 每次发布先写临时文件，三种格式全部校验通过后再原子替换。
- 任一步失败都保留上一版订阅。
- 如果本轮没有任何合格节点，而上一版订阅非空，则跳过发布，避免把空订阅推给客户端。
- 支持反向代理把 `&` 转成 `&amp;` 的兼容修复。

## 10. 定时下发

系统设置中可开启定时下发，两种模式：

### 10.1 每天固定时刻

默认 `04:30`。

- 到点触发。
- 15 分钟有效窗口。
- 如果上一轮还在跑，下一分钟重试。
- 批次失败或发布失败也在窗口内重试。
- 成功后才记为当天完成，每天一次。

### 10.2 固定间隔

默认 180 分钟，最小 5 分钟。

- 保存设置或上一次下发成功后开始计时。
- 失败在下一分钟重试，不会浪费整个间隔。
- 成功后才重新开始计时。

### 10.3 定时下发执行顺序

1. 暂停机场拉取；已在途的拉取最多等待 120 秒。
2. 对全部节点重新跑延迟检测 + 所有启用标签组。
3. 批次完整或用户停止后，按当前结果生成订阅。
4. 三种格式校验通过后原子替换线上文件。

## 16. 已知限制

- 单进程、单容器设计，面向个人或小规模使用。
- 节点数量很大时，每 200 个节点需要重载一次内核配置，大批次耗时较长。
- 相似分散只能降低同 IP / 同网段集中请求，无法识别共用机房或同一上游出口。
- 延迟检测通过不等于目标服务一定可用，目标站点的地区策略或风控仍可能影响实际使用。
- 输出格式以 Clash/Mihomo、sing-box、v2rayN 实测为准，其他客户端可能需要额外适配。
- 下载测速已包含，但不含上传测速、流媒体解锁检测、多用户权限、第三方订阅转换。
- 测速与延迟检测共用一套 Mihomo 配置，两者通过进程锁互斥；检测批次运行期间，手动测速会等待该批结束，超过 90 秒返回「已入队」而不是继续占用请求。

- 机场排除只影响测速，不影响延迟检测、评分、可用性和下发。

## 17. 常见问题

### 17.1 检测进度长时间停在一个百分比

先看仪表盘的阶段和「块 x/y」。每个节点在进度条上只算「2 个延迟目标 + 标签组数」，而一个延迟目标内部要跑 3 轮。某个延迟目标正在跑 3 轮时，进度不会每次请求都前进。

只要日志还在更新、阶段不是「已暂停」，就属于正常检测。若日志完全不动，检查内核是否可用、全局并发是否被占满，以及是否点了暂停。

### 17.3 节点能访问但不下发

按顺序检查：

1. 两个延迟目标是否都至少有一轮成功。
2. 成功的轮次是否没有超过各自上限。
3. 缓存池里的延迟数字是否标红。
5. 节点是否被停用机场或处于不可用状态。
6. 节点名/机场名/服务器地址是否命中「下发关键词过滤」（设置页可见，日志会记录「关键词过滤剔除 N 个节点」）。

### 17.4 自定义延迟上限重启后变回 1000

这是旧版本的迁移缺陷，已在 v1.2.28 修复。升级后重新保存一次上限即可长期保留。

### 17.5 登录后侧栏版本号显示 v1.0.0

旧版本在登录路由跳过了版本加载，已在 v1.2.29 修复。升级并强制刷新页面后应显示实际版本。

### 17.6 `/sub/all` 返回 403

- 检查 Token 是否与订阅输出页一致。
- 检查反向代理是否把 `&` 转义成 `&amp;`；后端已做兼容，但仍建议直接使用订阅输出页复制的完整链接。
- 重新生成 Token 后，旧链接会立即失效。
