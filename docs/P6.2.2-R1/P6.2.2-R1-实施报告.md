## 一、结论

P6.2.2-R1 已修正统一订阅批次的连接配置快照缺陷。统一订阅生成时，现在会冻结本批全部节点的 `protocol/server/port/params`，计算单节点与批次连接配置指纹；后续 P1 任一连接参数变化都会让旧批次变为 stale，四种格式下载统一返回 HTTP 409，重新生成后四格式共用最新配置、同一节点集合、同一展示名称和同一顺序。

本次只修改 P6.2.2 的连接配置快照、指纹、stale 判断、页面提示、测试和文档。P1–P5 未修改，P6.2.1 关键词规则未修改，四格式既定输出范围和标签规则未修改，未开放公网订阅或正式客户端拉取入口，未进入 P6.3/P7。

## 二、原实现缺陷

v2.047 的统一订阅批次只绑定：

- P6.1 最终优选版本；
- P6.2.1 规则修订号；
- 稳定 `node_id`、展示名和顺序。

下载与 stale 判断仍按稳定 `node_id` 从当前 P1 读取连接参数。因此当密码、UUID、协议、服务器、端口、TLS、Reality 或传输参数发生变化时，`node_id` 不变，旧批次会被误认为有效，继续按新配置渲染或下载，破坏批次快照一致性。

R1 将连接配置从“按 ID 临时读取”改为“生成时冻结 + 指纹校验”，并保持原有选点、过滤、合并、去重、标签和格式规则。

## 三、实现内容

### 3.1 生成时冻结连接配置

节点选择、机场、原始名称和评分仍只来自 P6.1；关键词过滤仍只来自 P6.2.1；P1 `np_nodes` 改为只读提供当前 `protocol/server/port/params`。

生成过程：

1. 校验 P6.1 当前版本与 P6.2.1 当前修订号。
2. 读取 P6.1 六类条目，按稳定 `node_id` 合并。
3. 合并 P6.2.1 过滤结果和命中原因。
4. 按稳定 `node_id` 从 P1 读取当前连接配置。
5. 规范化并计算每个节点的 `config_sha256`。
6. 任一节点在当前 P1 找不到连接配置，返回 `node_config_missing`，禁止生成。
7. 计算批次总指纹和 `config_node_count`。
8. 做四格式兼容性预检，形成统一 `output`。
9. 四格式共同使用这一份冻结的 `output_nodes` 生成内容。
10. 同一事务写入批次、四份输出、全部节点快照和事件。

P6.1 条目中的旧 `server/port` 不再作为最终端点，统一以 P1 当前值冻结。

### 3.2 连接配置规范化与指纹

单节点配置包含：

```json
{
  "protocol": "vless",
  "server": "10.0.0.3",
  "port": 443,
  "params": {
    "uuid": "...",
    "network": "ws",
    "security": "reality",
    "sni": "reality.example.com",
    "publicKey": "...",
    "shortId": "...",
    "fingerprint": "chrome"
  }
}
```

规范化规则：

- `protocol`：去首尾空格、转小写；
- `server`：去首尾空格；
- `port`：转整数；
- `params`：递归按键排序；移除 `null` 与空字符串；字符串保留原始大小写和内部空格，避免破坏密码、UUID、路径和公钥；
- canonical JSON 使用稳定键序、紧凑分隔符和 UTF-8。

指纹公式：

```text
node.config_sha256 = SHA256(canonical(protocol, server, port, params))

batch.config_sha256 = SHA256(
  "\n".join(f"{node_id}:{node.config_sha256}" for node_id in ascending order)
)
```

批次总指纹覆盖全部批次节点，包含 `filtered` 与 `unsupported`，不只覆盖最终输出节点。

### 3.3 存储与迁移

`np622_batches` 新增：

- `config_sha256`：批次总指纹；
- `config_node_count`：参与总指纹的节点数。

`np622_nodes` 新增：

- `params_json`：生成时冻结的完整有效连接参数；
- `config_sha256`：单节点指纹。

`store.ensure_schema()` 使用 `PRAGMA table_info` 检查旧库并执行 `ALTER TABLE`。v2.047 旧批次迁移后快照字段为空，自动识别为 `config_snapshot_missing` 并 stale；历史输出内容仍保留。

### 3.4 stale 判定

`_batch_stale_details()` 按以下顺序合并判断：

| 顺序 | 条件 | 代码 |
| --- | --- | --- |
| 1 | P6.1 版本不一致 | `p6_version_changed` |
| 2 | P6.2.1 修订号不一致 | `p621_revision_changed` |
| 3 | 批次总指纹/节点数缺失或与快照不一致 | `config_snapshot_missing` |
| 4 | 节点缺 `params_json/config_sha256` | `config_snapshot_missing` |
| 5 | 批次总指纹与节点快照重算不一致 | `config_snapshot_invalid` |
| 6 | 当前 P1 同 ID 节点缺失 | `node_config_missing` |
| 7 | 当前 P1 重算指纹与快照不同 | `node_config_changed` |

返回 `codes`、首个 `code`、可读 `reason`、`config_changed_count`、变化节点 ID、缺失数量和缺失节点 ID。多个原因可并存，页面按首个代码选择主标题，同时展示完整原因。

### 3.5 下载与四格式一致性

- `download()` 只针对最新批次。
- stale 判断使用完整详情，不再只判断版本和规则。
- 任一 stale 原因命中，四格式下载全部返回 HTTP 409，错误消息直接说明变化原因并要求重新生成。
- 历史批次格式预览返回生成时保存的 `content_text`，不会按当前 P1 重渲染；同时返回 `stale=true`。
- 重新生成产生新批次号，不更新历史批次；四格式共同使用同一批 `output_nodes`、同一展示名和相同顺序。

### 3.6 安全边界

- 普通 `summary`、`history`、`node_payload`、Dashboard、`np622_events.detail_json` 均不返回 `params_json`。
- 普通节点表只显示 `protocol/server/port/config_sha256` 前 12 位，不显示密码、UUID、Reality 公钥等参数。
- `status_reason` 不写入连接参数。
- 运行日志测试覆盖密码、UUID、Reality 公钥不出现。
- 订阅文件本身保留客户端正常连接所需的完整参数；仅管理员登录后可预览和下载，未新增公网订阅入口。后台格式预览显示的是本批真实订阅内容，因此仍包含连接参数，这是订阅文件语义所必需；普通列表、Dashboard 和日志已脱敏。

### 3.7 页面提示

`UnifiedSubscriptionP622.vue`：

- 顶部显示“连接配置 SHA”；
- 节点服务器行追加 `cfg <12位指纹>`；
- stale 横幅按 `stale_code` 区分版本、规则、连接配置、快照缺失等原因，并展示完整 stale 原因；
- 历史批次标签显示“配置已变化 / 版本已过期 / 规则已变化 / 需重新生成”，`title` 提供完整原因。

`Dashboard.vue`：

- stale 时显示 `${config_changed_count} 个连接配置变化`；
- 正常时显示“版本与配置一致”。
