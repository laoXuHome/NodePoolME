# P1 三层节点池实施报告

> 版本：v2.034  
> 实施日期：2026-11-28  
> 代码提交：`6f4a516`（`v2.034 实现 P1 三层节点池、双状态轴与来源历史`）  
> 前序基线：`561a45b`（v2.033）

## 1. 结论

P1 的三层节点池管理已完成并通过验证。原始池、健康池、观察池是同一批节点记录上的三个逻辑层级，不是三份节点副本；节点身份、机场来源、名称变化、两套状态轴与全部状态变化均有持久记录。单次检测失败、来源订阅删除、关键词过滤、竞争淘汰都不会删除原始记录。

本阶段没有实施任何网络探测、P80 延迟、异常复查调度、业务专项检测、七天质量评分、下载速度评价、智能竞争算法或最终订阅发布，P2 及后续阶段未被提前启动。

## 2. 实际完成的功能清单

### 2.1 原始节点池

- `np_nodes` 为每个机场、每个稳定身份保存一行；字段覆盖当前名称、首名、协议、端点、参数、地区、来源机场、订阅 URL、来源是否有效、首次/最近出现时间。
- 采集时把每个机场的全部标准化节点写入原始池，包括命中关键词、随后不会进入旧缓存池的节点。
- 节点从订阅中消失时仅置 `source_active=0` 并保留整行；不删除，也不清空历史身份。
- 旧缓存池的全量替换逻辑不会传导到 P1：`fetcher._upsert()` 先把本次采集结果写入 P1，再执行原有替换；即使旧缓存被清空，P1 记录仍保留。
- 首次启用 P1 时自动回填当前 `nodes` 与未准入的 `airport_filtered_nodes`，不需要人工迁移。

### 2.2 健康节点池

- `management_layer=healthy` 表示基础管理层通过。
- 准入条件固定为基础健康 `healthy`、数据状态 `sufficient`、来源 `source_active=1`；任一不满足都不会进入健康池。
- 进入健康池只赋予基础管理资格，不自动等于智能优选；健康池节点的竞争状态默认从 `observation` 变为 `candidate`，优选仍需显式状态操作。
- 失去健康资格（不健康、未知、数据不足、来源消失）自动转入观察层，同时保留基础健康状态值，便于区分“健康不合格”和“只是观察中”。

### 2.3 观察节点池

- `management_layer=observation` 承接：新采集、数据不足、基础异常待确认、状态波动、近期质量下降、来源暂时消失、等待恢复确认。
- 观察原因写入 `observation_reason`，支持按层、按原因文本、按健康/竞争/数据状态查询。
- 观察节点不删除，仍可通过 `POST /api/nodepool/nodes/{id}/health` 接收后续检测结论；恢复为“健康 + 数据充足 + 来源有效”后可正常回到健康池。
- 观察节点与健康节点使用同一行记录，转换只改字段并写审计事件。

### 2.4 两套独立状态轴

- 基础健康：`base_health = healthy | unhealthy | unknown`。
- 智能竞争：`competition_state = candidate | preferred | observation | eliminated`。
- 两轴独立存储，互不覆盖。节点可以“基础健康”但“竞争淘汰”，也可以“基础不健康”但保留历史淘汰记录。
- 淘汰只改竞争状态，不删除节点，不改变原始池成员关系。
- `np_node_qualifications` 支持同一节点同时持有多个业务资格（如 `streaming`、`download`），支持授予、撤销与历史记录。

### 2.5 节点身份、来源与名称历史

- 稳定身份 `identity_key`：由协议、规范化服务器、端口、传输参数生成，**名称不参与身份计算**；改名不产生新节点。
- 同一机场、同一身份下的重复配置用 `occurrence` 区分，保留机场发布的多个同端点节点，不按 server 合并。
- 同批次重复采集按“原名优先匹配、出现序号兜底”分配身份；再次采集同名节点复用原行。
- `np_node_names` 保存每个历史名称的首次/最近出现与出现次数；`first_name` 永久保留首名。
- `source_name`、`source_url`、`source_active` 保留机场来源及有效性；`np_node_events` 记录 `node_ingested`、`name_changed`、`source_missing`、`source_returned`、`health_update`、`layer_transition`、`competition_update`、资格授予/撤销等事件。

### 2.6 层级转换与审计

- 转换只更新 `np_nodes` 同一行，不复制记录；不会因层级变化产生重复节点。
- 所有转换校验在服务层完成：健康池要求三项准入；候选/优选要求节点已在健康池且基础健康合格；不满足返回稳定错误码 `not_health_eligible` / `not_competition_eligible`。
- 每次变化写入 `np_node_events`，包含前后层级、前后两轴状态、原因、操作者与详情 JSON。
- 原始池始终包含全部记录；统计中的 `raw_total = healthy + observation + raw_only`，不会把健康池/观察池算成额外副本。

### 2.7 管理查询与展示

后端接口（均需登录）：

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| GET | `/api/nodepool/summary` | 三层总量、两轴分布、数据状态、来源有效/历史、按机场统计 |
| GET | `/api/nodepool/nodes` | 按层、健康、竞争、数据、机场、来源、关键词分页查询 |
| GET | `/api/nodepool/nodes/{id}` | 节点详情、名称历史、状态事件、资格历史 |
| POST | `/api/nodepool/nodes/{id}/health` | 接收 P2/P3 健康与数据结论（P1 不探测） |
| POST | `/api/nodepool/nodes/{id}/layer` | 人工层级转换 |
| POST | `/api/nodepool/nodes/{id}/competition` | 人工竞争状态转换 |
| POST | `/api/nodepool/nodes/{id}/qualifications` | 授予业务资格 |
| DELETE | `/api/nodepool/nodes/{id}/qualifications/{name}` | 撤销业务资格 |

控制台新增「三层节点池」页：

- 四张统计卡：原始池全部、健康池、观察池、仅原始层；卡内展示来源有效/历史、健康/候选、数据不足/不健康、淘汰/资格数量。
- 节点表与移动端卡片展示管理层、基础健康、竞争状态、数据状态、来源有效性、观察原因、资格。
- 详情抽屉展示稳定身份、来源、端点、首名/现名、名称历史、状态审计、资格；提供健康、层级、竞争、资格的管理按钮，便于验收 P1 管理能力。
- 页面明确标注：健康/数据结论由 P2 写入，本页按钮不发起网络探测。

## 3. 技术实现要点

### 3.1 数据结构

新增 6 张旁路表：

- `np_nodes`：节点库存与两轴状态（唯一键 `airport_id + identity_key + occurrence`）。
- `np_node_names`：名称历史。
- `np_node_events`：状态与身份审计。
- `np_node_qualifications`：多业务资格，活动资格唯一。
- `np_fetch_batches`：每次采集的 seen/new/changed/missing 摘要。
- `np_meta`：回填标记。

### 3.2 不破坏既有基线

- 没有修改 `db.SCHEMA`、`BASE_TABLES` 的 17 张冻结业务表，也没有给 `nodes` 加列。
- P1 表在第一次采集或第一次访问 P1 API 时懒创建；既有数据库不需要停机迁移。
- P1 表会进入 `structure_hash()`，因此 `migrate.SUPPORTED_STRUCTURE_PROFILES` 增补 `alter_history_p1`、`fresh_init_p1` 两个已登记形态，备份/体检仍可通过 `structure_profile_for` 校验；原有两个基线档案保持不变。
- 备份实际包含 P1 六张表，导出、`verify_backup` 与计数校验均正常。

### 3.3 采集接线

`fetcher._upsert()` 在原有事务内、旧缓存替换之前调用 `nodepool.ingest_fetch(conn, airport_id, fetched)`：

- 采集和 P1 入库同事务，失败一起回滚。
- P1 的 `source_active` 只表达“本次订阅是否仍发布该节点”，不表达节点是否可用。
- 原 `nodes` 全量替换、关键词过滤、准入搬表逻辑保持原样，订阅输出链路不受影响。

### 4.2 验收项逐条对照

| 验收要求 | 结果 | 验证 |
| --- | --- | --- |
| 新采集节点进入原始节点池 | 通过 | 新采集后 `raw_total` 增加，层为观察，原因 `new` |

| 观察状态可识别查询 | 通过 | `layer=observation`、观察原因与数据状态均可筛选 |

### 4.3 采集替换场景验证

- 同一指纹节点改名后再次采集：旧缓存更新名称，P1 仍为同一行，名称历史为 2 条。
- 订阅返回空列表：旧 `nodes` 表按原逻辑清空，P1 行保留，`source_active` 变为 false，层为观察，未被删除。
- 订阅少返回一个节点：P1 标记该节点 `source_missing`，其余节点保持不变；节点重新出现后恢复来源有效并回到观察待复查。

## 5. 未完成事项及原因

P1 范围内没有未完成的功能项。以下均为任务明确排除、按阶段边界不实施的能力：

- DNS/TCP/TLS/HTTPS 基础检测与 P80 延迟计算：P2。
- 异常复查、自动恢复调度、状态波动自动判定：P2/P3。
- 业务专项检测：后续阶段。
- 七天质量评分、下载速度评价：后续阶段。
- 智能竞争算法：后续阶段；P1 只提供 `candidate/preferred/observation/eliminated` 状态容器与管理入口。
- 最终订阅发布：后续阶段，P1 未改动现有订阅输出。

已知边界（不是缺陷）：同一机场发布多条“协议/端点/参数完全相同”的重复节点时，P1 以名称优先、出现序号兜底保持行稳定；如果机场同时重排并重命名这些完全同构的节点，物理同一性无法从订阅内容本身证明，P1 只保证不重复、不丢失并保留全部名称历史。
