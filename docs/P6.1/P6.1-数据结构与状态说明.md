# NodePoolME P6.1 数据结构与状态说明

## 一、总体原则

P6.1 是 P5 下游的只读投影层。数据源只有：

- `np5_state`：读取 `state='preferred'`；
- `np5_runs`：读取最近一轮状态，作为版本有效性门槛；
- `np_nodes`、`airports`：读取节点名、机场、服务地址，用于结果展示。

P6.1 不写 P1 节点、P2 健康、P3 业务资格、P4 质量、P5 竞争状态或竞争评分。

## 二、类别

固定六类，键值与 P5 一致：

| 键 | 名称 |
|---|---|
| `standard` | 标准综合优选 |
| `gpt` | GPT 专项优选 |
| `youtube` | YouTube 专项优选 |
| `telegram` | Telegram 专项优选 |
| `github` | GitHub 专项优选 |
| `global` | 国外综合专项优选 |

## 三、表结构

### 1. `np6_versions`

版本头，只追加。

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | INTEGER PK | 内部版本 ID |
| `version_no` | TEXT UNIQUE | 展示版本号，`P6.1-0001` |
| `created_at` | TEXT | 生成时间 |
| `trigger` | TEXT | `manual` / `auto` / `startup` / `cli` |
| `valid` | INTEGER | 有效状态，当前版本均为 1 |
| `is_empty` | INTEGER | 是否有效空版本 |
| `total_nodes` | INTEGER | 六类条目总量（同节点跨类重复计数） |
| `category_counts_json` | TEXT | 六类各自数量 |
| `change_counts_json` | TEXT | 六类各自新增/移除/保留 |
| `previous_version_id` | INTEGER | 上一有效版本 ID |
| `previous_version_no` | TEXT | 上一有效版本号 |
| `source_run_id` | INTEGER | 来源 P5 轮次 |
| `source_run_at` | TEXT | 来源 P5 完成时间 |
| `signature` | TEXT | 六类成员 ID 排序后的 SHA-256 |
| `detail_json` | TEXT | 汇总附加信息 |

### 2. `np6_entries`

某一版本的完整优选节点，也是内部待定订阅池。

| 字段 | 说明 |
|---|---|
| `version_id` | 所属版本 |
| `category` | 六类之一 |
| `node_id` | P1 节点 ID |
| `node_name` / `airport_id` / `airport_name` | 节点与机场 |
| `server` / `port` | 服务地址 |
| `score` / `maturity` / `p80_ms` | 写入时证据 |
| `delay_grade` / `speed_grade` / `speed_mb_s` | 写入时评价 |
| `preferred_since` | P5 优选起点 |
| `last_reason` | P5 最近原因 |
| `detail_json` | P5 状态附加详情 |

主键：`(version_id, category, node_id)`。同一版本同一类别内节点唯一；同一节点可出现在不同类别。

### 3. `np6_changes`

版本差异流水。

| 字段 | 说明 |
|---|---|
| `version_id` | 当前版本 |
| `previous_version_id` | 上一版本 |
| `category` | 类别 |
| `node_id` | 节点 |
| `change_type` | `added` / `removed` / `retained` |
| `at` | 本次变化时间（即版本生成时间） |
| `trigger` | 触发原因 |
| `node_name` / `airport_name` | 记录时名称 |
| `before_score` / `after_score` | 变化前后分数 |
| `detail_json` | 变化前后完整条目 |

每类独立计算、独立落行。节点从 A 类退出并进入 B 类时，会在 A 类产生 `removed`、B 类产生 `added`。

### 4. `np6_events`

运行审计，记录 `snapshot_created`、`snapshot_unchanged`、`snapshot_rejected`，包含时间、版本、触发原因和详情。

## 四、版本生成状态机

```text
无 P5 轮次            -> 拒绝（no_p5_run）        -> 保留上一有效版本
P5 running / partial  -> 拒绝（run_not_success）   -> 保留上一有效版本
P5 success + 签名相同  -> 不生成（unchanged）       -> 记录事件
P5 success + 签名变化  -> 生成新版本
P5 success + 无 preferred -> 生成有效空版本（is_empty=1）
```

签名只取“类别 + 节点 ID”，不把分数、成熟度、延迟等波动纳入版本判定。只有成员变化才产生新版本。

## 五、有效性语义

- **有效版本**：由 P5 最近一轮 `success` 的 `preferred` 快照产生；`valid=1`。
- **有效空版本**：P5 成功且六类确实没有 `preferred`；`is_empty=1`，`total_nodes=0`，不继承上一版本节点。
- **无效结果**：P5 未成功或不存在成功轮次；不落版本，只在 `np6_events` 记录拒绝。
- **当前版本**：`np6_versions` 中 `id` 最大的版本；历史版本不参与当前查询。

## 六、只读查询语义

- `GET /api/final/*` 不生成版本，只读取 `np6_*` 和 P5 源状态。
- 刷新页面、重复请求、切换分类、打开历史版本均不改变 `np6_versions`。
- 差异直接读取 `np6_changes`，不重新计算当前 P5 状态，因此历史差异不会随 P5 后续变化而漂移。
- `POST /api/final/snapshot` 是唯一生成入口；页面按钮调用该接口。

## 七、接口响应要点

`GET /api/final/current`：

```json
{
  "version": {
    "version_no": "P6.1-0002",
    "created_at": "2026-11-28 15:53:31",
    "trigger": "auto",
    "valid": true,
    "is_empty": false,
    "total_nodes": 22,
    "category_counts": {"standard": 4, "gpt": 4, "youtube": 3},
    "change_counts": {"standard": {"added": 1, "removed": 1, "retained": 3}},
    "previous_version_no": "P6.1-0001",
    "source_run_id": 2
  },
  "categories": [
    {"code": "standard", "count": 4, "nodes": []}
  ],
  "diff": {"categories": []}
}
```

`GET /api/final/diff` 的每条变化包含 `category`、`node_id`、`change_type`、`at`、`trigger`、`node_name`、`airport_name`，可按类别追溯到上一有效版本。

## 八、与后续阶段的数据边界

- 待定订阅池 = 当前版本 `np6_entries`，不是健康池，不是发布订阅。
- 后续关键词过滤只能作用于下发出口，不得修改 `np6_entries` 或历史快照。
- P6.1 不创建订阅表、不写订阅文件、不暴露客户端拉取路由。
