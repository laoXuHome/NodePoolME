## 一、交付范围

P2 在 P1 三层节点池之上增加一套独立的健康检测链路，检测结果只改基础健康、数据状态、管理层和观察原因，不触碰 P1 竞争轴。

实际交付包括：

1. 独立健康模块 `backend/health/`：目标与历史存储、分阶段探测、轮次判定、调度与恢复、目标自测。
2. 9 张 `np2_*` 旁路表，不修改冻结的 17 张 P1 基线表。
3. 13 个 `/api/health/*` 接口，均要求登录。
4. 后台页面 `/health`「基础健康」，侧栏第 5 项，桌面表格与移动端卡片双布局。
5. 调度接入现有 APScheduler，5 秒 tick，全局并发和同节点队列唯一约束。
6. P1 联动入口 `apply_probe_health_conn` / `apply_probe_health`，只更新基础健康轴，保留竞争状态与节点原始身份。

新增表：`np2_targets`、`np2_target_checks`、`np2_node_state`、`np2_checks`、`np2_target_results`、`np2_stage_results`、`np2_tcp_samples`、`np2_queue`、`np2_events`。当前库结构为 17 张基表 + P1 6 张表 + P2 9 张表，共 32 张。

## 二、关键实现

### 1. 检测目标管理

默认启用两个目标：

| 目标 | 地址 |
| --- | --- |
| Google | `https://www.google.com/generate_204` |
| Wikipedia | `https://www.wikipedia.org/` |

支持改名、改地址、新增、删除、启停、手动测试、恢复默认。至少保留 2 个启用目标，推荐 2–5 个。

配置版本规则：改名不失效历史；地址、启停、新增、删除会提升 `p2_config_version`，清空旧轮次结论，把节点转回观察池并全量重排。在途检测若仍使用旧版本，落库时标为 `config_changed`，不参与状态判定。

### 2. 分阶段探测

每个目标独立执行，严格短路：

1. DNS：1 次，3 秒；保存成功状态、耗时、解析地址。解析失败即 Unknown，后续 TCP/TLS/HTTPS 全部 `unexecuted`。
2. TCP：5 次，每次 3 秒，间隔 1 秒；保存 5 条原始样本。连接失败独立记录，不伪造延迟。
3. TLS：1 次，5 秒；保存握手状态、耗时、证书状态。失败后 HTTPS 不执行。
4. HTTPS：1 次，8 秒；保存状态码、响应耗时和关键响应头。

单目标硬 deadline 20 秒。DNS、TLS、HTTPS 耗时只作辅助分析，不与 TCP P80 相加。

生产环境节点探测经 Mihomo 的每节点 SOCKS listener 发起；目标自身是否可达另做控制端直连 selftest。selftest 不可用时，该目标在本轮对节点统一返回 Unknown，不会把目标故障算成节点故障。

### 3. TCP P80

只使用 5 个有效延迟样本。按最近秩法计算：

\\[
\\text{rank}=\\lceil 0.8 \\times n \\rceil
\\]

5 个样本时 rank=4，排序后取第 4 个值作为正式 P80。不使用中位数、均值、最低值或最高值。少于 5 个有效样本时按实际有效样本数计算并保存有效样本数；无有效样本时 P80 为空。

延迟等级严格按已确认阈值：≤150 优秀、151–250 良好、251–400 正常、401–500 较差、501–800 严重、>800 不合格。

### 4. 归因

每轮按每个启用目标独立归类：

- 有效成功：Success。
- 节点路径确认失败：Failure。
- 目标不可用、检测服务异常、责任无法确认的超时、任务中断、系统异常、数据不完整：Unknown。

轮次规则：任一目标有效 Failure 即本轮 Failure；没有 Failure 但存在 Unknown，本轮 Unknown；所有目标成功才可能 Success。Unknown 不增加连续失败/成功计数，不覆盖此前的有效健康结论，也不触发淘汰。

### 5. 状态机与调度

- 正常周期默认 30 分钟，可在 5–1440 分钟范围修改。
- 观察节点每 5 分钟复查；不健康节点每 5 分钟做恢复检查。
- 第 1 次有效失败进入异常待确认，约 15 秒后快速复查；第 2 次失败约 30 秒后再查；第 3 次有效失败判不健康。
- 连续 2 次有效成功恢复健康资格，再按 P1 规则回到相应层级。
- 快速复查重新执行完整四阶段，不复用上一次结果。
- 同一节点由 `uq_np2_queue_active` 部分唯一索引保证只占一个 pending/running 队列位置。
- 批次内节点并发，并发数默认 10、可配置 1–50；批次之间串行，避免同时改 Mihomo 配置。
- 任务超时释放队列；60 秒是快速复查调度目标，不作为硬保证。

### 6. P1 联动

只有达到第 3 次有效失败或第 2 次连续成功时才写 P1：

- 健康且数据充足、来源有效：进入健康池。
- 新节点、数据不足：观察池。
- 异常待确认：观察池。
- 不健康：不得继续作为健康节点参与优选。
- Unknown：不直接把节点改成不健康。
- 恢复后按 P1 规则重新进入健康池。
- 节点身份、来源、名称历史、竞争状态不因健康状态变化而丢失。

## 三、验证结果

### 1. P80 计算验证

直接调用生产函数，结果如下：

| 输入 5 个样本 | 排序后第 4 个 | 函数输出 |
| --- | --- | --- |
| 72, 82, 92, 112, 122 | 112 | 112 |
| 650, 90, 110, 130, 100 | 130 | 130 |
| 100, 200, 300, 400, 500 | 400 | 400 |
| 151, 150, 250, 251, 400 | 251 | 251 |
| 501, 800, 600, 700, 520 | 700 | 700 |

边界等级实测：150 优秀、151 良好、250 良好、251 正常、400 正常、401 较差、500 较差、501 严重、800 严重、801 不合格。

控制台详情同时显示 5 条原始样本和“取排序后第 4 个值”的说明，不是只给一个结果数字。

### 2. Failure 与 Unknown 验证

| 场景 | 轮次分类 | 连续失败计数 | 节点状态 |
| --- | --- | --- | --- |
| 单目标 TCP 全失败 | Failure | +1 | exception，15 秒复查 |
| 第 2 次有效失败 | Failure | +1 | exception，30 秒复查 |
| 第 3 次有效失败 | Failure | +1 | unhealthy，5 分钟恢复检查 |
| 全部目标 selftest 不可用 | Unknown | 不变 | 保留原健康结论 |
| DNS 失败 | Unknown | 不变 | 后续阶段 unexecuted |
| 旧配置在途结果 | 丢弃 | 不变 | 标记 config_changed，不参与判定 |

专项测试覆盖了“单次失败不立即不健康”“Unknown 不计数不覆盖”“目标全故障不批量误杀”“DNS 失败后续阶段 unexecuted”。

### 3. 异常复查与恢复

专项测试实际走完以下链路：

1. 第 1 次失败：`exception`，下次约 15 秒。
2. 第 2 次失败：`exception`，下次约 30 秒。
3. 第 3 次失败：`unhealthy`，下次 5 分钟。
4. 恢复成功 1 轮：`recovering`。
5. 恢复成功 2 轮：`healthy`。

调度测试注入了目标探测、端口准备和节点探测，实际跑完 `tick → 入队 → 批次 → 落库 → P1 联动`，验证新节点一轮成功即进入健康池。

### 4. 真实网络链路

在当前云主机上对公网 HTTPS 目标执行完整 DNS → TCP×5 → TLS → HTTPS：

- 结果：Success。
- 5 次 TCP：30、27、31、29、30 ms。
- 最近秩 P80：30 ms，等级优秀。
- TLS：98 ms；HTTPS：200；总耗时 4413 ms。
- 四阶段均执行，无伪造阶段。

同一环境访问 Google 的 TCP 五次均失败，节点结果按 Unknown 处理，不归咎节点。这是当前出口网络限制，不代表目标配置或检测代码错误。Google、Wikipedia 的真实可达性需在部署网络验收。

## 五、边界与遗留

本阶段未实施：P3 业务专项检测、P4 七天质量与下载速度、P5 智能竞争、P6 关键词过滤与订阅发布、P7 决策历史完整分析。

需要项目负责人注意的取舍：

1. 地址、启用、新增、删除目标会按需求清空旧结论并全量重检，代价是短期所有节点回到观察池。当前按“旧配置数据不能作为新配置依据”严格执行。
2. 目标 selftest 从控制端直连；若部署网络本身长期不可达 Google/Wikipedia，节点会持续 Unknown。这是按“目标自身故障归 Unknown”实现的结果，需现场确认出口网络。
3. P2 节点探测依赖 Mihomo 每节点 SOCKS listener。当前云主机没有该环境，真实节点 SOCKS 批次还需在具备 Mihomo 的部署环境跑一轮。
4. P2 批次与旧测速/发布共享 Mihomo 配置操作锁；批内并发已生效，跨批次串行，尚未对照旧订阅发布链路做真实并发压测。

P2 完成后停止，等待项目负责人验收，不进入 P3。
