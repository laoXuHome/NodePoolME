## 三、统一生成链路

### 3.1 数据读取顺序

1. 读取当前 P6.1 `latest_version()` 和六类 `np6_entries`。
2. 强制 `filter_store.ensure_preview()`，保证 P6.2.1 预览绑定当前 P6.1 版本与当前 `rule_revision`。
3. 以 `node_id` 聚合同一稳定节点，保留其全部命中类别，形成合并记录、唯一节点和重复数量。
4. 读取当前版本、当前修订号的 `np621_results`，按节点合并跨类别命中原因。
5. 按稳定 `node_id` 关联 P1 `np_nodes`，仅补全 `protocol` 与 `params`；服务器、端口、机场、名称、评分仍使用 P6.1 快照。
6. 生成业务标签与最终展示名。
7. 排除关键词命中节点，再排除不能被四种格式同时正确表达的节点。
8. 对同一输出集合分别构建四种格式，逐格式校验并写入同一批次。

### 3.2 版本闸门

每次 summary、format、download、generate 都先执行 `ensure_preview()`。以下任一情况直接抛 `UnifiedError`，不生成：

- 当前没有 P6.1 版本；
- P6.2.1 预览未绑定当前 P6.1 `version_id`；
- 预览的 `rule_revision` 与当前规则集不一致；
- `np621_results` 缺少合并节点。

旧批次遇到 P6.1 版本或规则变化时标记 `stale`；`GET /download/{fmt}` 返回 409，避免把旧过滤结果当成新订阅下载。历史批次仍可通过 `GET /formats/{fmt}?batch_id=` 查看，并明确带 `stale=true`，仅用于追溯。

## 五、四格式生成与一致性

四种格式使用同一个 `output` 列表、同一顺序和同一 `display_name`。演示批次实际结果：

| 格式 | 文件名 | 状态 | 节点 | 字节 | 内容 SHA256 |
| --- | --- | --- | --- | --- | --- |
| Clash / Mihomo | `nodepool-unified.yaml` | success | 5 | 2,082 | `82fda877875615a110eb9ca61e218133ef908946ba8c693658f5509ef8b25ef4` |
| sing-box | `nodepool-unified.json` | success | 5 | 3,528 | `b3750b16f015709f471ec9ca01294caa59e65a72301363d0af7dd77e4704e452` |
| 通用 Base64 | `nodepool-unified.base64.txt` | success | 5 | 1,184 | `1e6d3e15e800621f1b0c5ceee6e9154e69dd88868dbe33c79860edf2e56a359a` |
| Loon | `nodepool-unified.loon.txt` | success | 5 | 1,036 | `90b7c5e6bb3fd1c2e1e0b960f4a8064b6f830f18e619e823c8127bf2931056a9` |

生成后逐格式执行结构校验：Clash 校验 `proxies` 数量与名称集合；sing-box 校验节点 outbound 数量与 tag 集合；Base64 校验节点行数与解码后的名称；Loon 校验节点行数和 URI 协议前缀。任一格式构建或校验失败会记录真实 `failure_reason`，该格式状态为 `failed`；单格式失败时批次为 `partial`，全失败时为 `failed`，不会把失败格式写成成功。

### 5.1 格式兼容性口径

四种格式节点数量一致，这是本批的硬约束。Loon 无法表达所有协议，因此生成前先做兼容性预检。不能被四种格式同时正确表达的节点（如 Loon 不支持的 `tuic`、`hysteria` v1、`http`/`socks` 等）从统一输出集合中统一排除，并记录：

- 批次 `compatibility_excluded_count`；
- `unsupported_json` 的节点、协议、逐格式原因；
- 节点状态 `unsupported`，页面标记“格式不兼容”。

该处理不伪造节点、不让某一格式静默少节点、也不因单个协议导致整批失败。被排除节点仍保留在批次节点快照中，便于管理员核查。

## 六、协议参数保留

四格式复用 `backend/parsers/subscription.py` 与 `backend/subscriptions/builder.py` 的协议解析和格式能力；P6.2.2 仅补全 P6.1 未保存的 `protocol/params`，并统一封装。

已验证：

| 协议 | 关键参数 | 验证结果 |
| --- | --- | --- |
| SS | cipher、password、server、port | 四格式保留 |
| VMess | UUID、alterId、cipher、WS path/Host、TLS、SNI、ALPN | Clash `ws-opts`、sing-box `transport`、Base64、Loon 均保留 |
| VLESS + Reality | UUID、WS、SNI、publicKey、shortId、fingerprint、ALPN | Clash `reality-opts`、sing-box `reality`、Base64 `pbk/sid`、Loon `security=reality` 均保留 |
| Trojan | password、SNI、ALPN、传输方式 | 四格式保留 |

Base64 对 URI 片段中的 `#`、空格和 `%` 做转义，避免去重后缀 ` #2` 被客户端解析成只剩 `2`。VMess 名称在 JSON 内、SSR 名称在 remarks 内，不做 URI 片段转义。

5. 节点预览：最终名称、原始名、机场、服务器、协议、速度、业务标签、状态与命中原因；被过滤节点仅在此展示。

移动端 390px 下导航压缩为 21px 图标，页面单列排布，无横向溢出。

Dashboard 新增独立块“统一订阅生成 · P6.2.2”，展示最终节点、过滤数、GPT/YT/TG/GH、最近生成、版本/规则、批次状态和四格式状态。数据来自 `np622_batches` / `np622_outputs`，不使用演示常量。

## 八、批次记录与状态

每次生成创建新的 `np622_batches`，同批写入四行 `np622_outputs` 和完整 `np622_nodes` 快照。记录为追加式，不提供更新或删除接口。重复生成只新增批次，不创建 P6.1 版本、不改 P6.2.1 规则、不触发 P2/P3/P4/P5。

- 节点状态：`allowed / filtered / unsupported`。
- 批次状态：`success / partial / failed / empty`。
- 页面状态：`not_generated / success / partial / failed / empty / stale`。
- `candidate_count = unique - filtered`；`output_count = candidate - compatibility_excluded`。

## 九、边界与禁止项核对

| 禁止项 | 结果 |
| --- | --- |
| 修改 P1–P5 | 未修改既有逻辑；仅读取 P1 协议参数、P5 类别定义 |
| 修改 P6.1 历史快照 | 只读 `latest_version` / `entries_of` |

| 六类独立订阅 | 无；只有一个统一输出集合 |
| 暴露机场原始 URL/凭据 | 订阅内容与批次均不保存机场 URL；测试覆盖泄露检查 |
| 公网发布/客户端拉取 | 无正式入口；仅登录后台预览和管理员下载 |
| 修改既有发布计划 | `backend/subscriptions/builder.py` 旧发布链未改动 |
| 修改原始名称/协议参数 | 名称仅生成展示名；参数仅从 P1 补全，不转换协议 |
