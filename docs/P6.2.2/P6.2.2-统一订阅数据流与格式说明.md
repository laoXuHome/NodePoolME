# P6.2.2 统一订阅数据流与格式说明

- 版本：v2.048（P6.2.2-R1）
- 适用批次：P6.2.2
- 定位：说明统一订阅从哪里取数、如何合并/过滤/命名、如何冻结连接配置、如何生成四种格式，以及版本、规则与连接配置如何共同约束批次

## 一、端到端数据流

```text
机场采集
→ P1 原始节点池（当前 protocol / server / port / params）
→ P2 基础健康检测
→ P3 业务专项检测
→ P4 七天质量与下载速度评价
→ P5 六类智能节点竞争
→ P6.1 六类最终优选版本（唯一节点选择、机场、名称、评分来源）
→ P6.2.2 六类合并 + 稳定 node_id 去重
→ P6.2.1 当前规则 + 当前版本关键词过滤（唯一过滤来源）
→ P1 当前连接配置只读关联
→ 参数规范化 + 每节点连接配置指纹
→ GPT / YT / TG / GH 服务标签
→ 统一展示名
→ 四格式兼容性预检
→ 连接配置快照写入 np622_nodes
→ Clash / sing-box / Base64 / Loon 同一集合输出
```

P6.2.2 不接入 P1 采集、P2/P3/P4 检测、P5 竞争或旧发布链。P1 的 `np_nodes` 以只读方式提供当前协议、服务器、端口和参数；节点选择、机场、原始名称、评分和业务资格仍来自 P6.1。连接配置一旦进入批次，就成为不可变快照，后续 P1 修改不覆盖历史批次。

## 二、来源表与读取入口

| 来源 | 读取内容 | 用途 |
| --- | --- | --- |
| `np6_versions` / `np6_entries` | 当前版本、六类条目 | 合并去重、标签、机场、名称、评分 |
| `np621_state` / `np621_results` | 当前修订号、当前预览、命中原因 | 关键词过滤与版本闸门 |
| `np_nodes` | `protocol`、`server`、`port`、`params` | 按稳定 `node_id` 只读补全连接配置，不参与选点 |
| `np622_batches` | 批次汇总、连接配置总指纹 | 概况、历史、Dashboard、stale 判断 |
| `np622_outputs` | 四格式状态与生成时内容 | 预览、下载、SHA/字节 |
| `np622_nodes` | 批次节点快照、参数快照、节点指纹 | 历史追溯、配置变化判断、管理预览 |

## 三、合并与去重

1. 对六类 `np6_entries` 取并集。
2. 以稳定 `node_id` 为唯一键聚合；同名不同 ID 不合并。
3. 同一节点跨类出现时，`categories`、`labels`、命中原因取并集，只输出一次。
4. 不固定数量、不补位；六类全空时仍可生成空批次。
5. 合并只读，不修改 P5 状态、P6.1 条目和版本。

批次字段记录：

- `merged_count`：合并前记录数；
- `unique_count`：稳定 ID 去重后节点数；
- `duplicate_count = merged_count - unique_count`；
- `category_counts_json`：六类各自数量。

## 四、业务标签与展示名

只认 P6.1 六类：`gpt→GPT`、`youtube→YT`、`telegram→TG`、`github→GH`。`standard`、`global` 不产生标签。顺序固定 `GPT→YT→TG→GH`，去重后拼接。

展示名：

```text
速度等级 emoji + 机场名 + "·" + 标签段 + "·" + P6.1 原始节点名
```

无标签时省略标签段。P6.1 原始名称不改。若两个不同节点的最终展示名完全相同，只对后一个展示名追加 ` #2`、` #3`，确保客户端不因重名吞节点。四种格式共同使用同一展示名和同一顺序。

## 五、P6.2.1 过滤绑定

不重新实现关键词匹配，只消费当前 `np621_results`：

- 版本：`p6_version_id` 必须等于当前 P6.1 `version_id`；
- 修订：`rule_revision` 必须等于 `np621_state.rule_revision`；
- 完整性：合并节点必须能在结果中找到；
- 同一节点跨类命中时，`reason` 取并集，保留 `rule_id`、`keyword`、`field`、`field_label`、`value`。

命中节点：

- `status=filtered`；
- 不进入任何客户端内容；
- 仍在 `np622_nodes` 和管理预览中保留标签、分数、命中原因；
- 不撤销 P5/P6.1 资格。

## 六、连接配置快照与指纹（R1）

### 6.1 冻结字段

每个进入批次快照的稳定节点保存：

- `protocol`
- `server`
- `port`
- `params` 全量有效连接参数
- `config_sha256` 单节点连接配置指纹

批次另存：

- `config_sha256`：全部批次节点指纹按 `node_id` 排序后的总指纹
- `config_node_count`：参与总指纹计算的节点数

上述字段写入 `np622_nodes` / `np622_batches`，生成后只读。历史批次的 `params_json` 不会被后续 P1 修改覆盖。

### 6.2 指纹算法

参数先规范化，再生成稳定 JSON：

```text
config = {
  protocol: 去空格并小写,
  server:   去首尾空格,
  port:     int,
  params:   递归排序键；去掉 null 与空字符串；保留密码/UUID/路径等原始大小写与空格
}
canonical = json.dumps(config, sort_keys=True, separators=(",",":"), ensure_ascii=False)
config_sha256 = SHA256(canonical)
```

批次总指纹：

```text
parts = 按 node_id 升序的 "node_id:config_sha256"
batch_config_sha256 = SHA256("\n".join(parts))
```

指纹覆盖协议、服务器、端口与全部有效参数，包括密码、UUID、TLS SNI/ALPN/指纹、Reality `publicKey/shortId`、传输 `network/path/host/serviceName`、SS 加密与插件参数等。

### 6.3 stale 判断

页面读取、格式预览、下载和生成前都会检查：

1. 批次 `p6_version_id` 是否等于当前 P6.1 版本；
2. 批次 `p621_revision` 是否等于当前 P6.2.1 修订号；
3. 批次是否有完整 `config_sha256/config_node_count`；
4. 批次节点是否都有 `params_json/config_sha256`；
5. 批次总指纹是否与节点快照重算结果一致；
6. 按稳定 `node_id` 读取当前 P1 `protocol/server/port/params`，重算指纹并与批次逐节点比较；
7. 当前 P1 节点缺失也视为配置不可用。

任一条件不满足，批次 `stale=true`，下载返回 HTTP 409。旧批次只读保留，不能继续作为当前订阅下载。

stale 代码：

| 代码 | 含义 |
| --- | --- |
| `p6_version_changed` | P6.1 最终优选版本已变化 |
| `p621_revision_changed` | 关键词规则修订号已变化 |
| `node_config_changed` | 一个或多个节点连接配置已变化 |
| `node_config_missing` | 当前 P1 找不到某节点连接配置 |
| `config_snapshot_missing` | 批次或节点缺少 R1 连接配置快照 |
| `config_snapshot_invalid` | 批次总指纹与节点快照不一致 |

多个原因可同时存在，`stale_codes` 返回全部，`stale_code` 返回首个原因，`stale_reason` 返回可读说明；Dashboard 与批次历史同步展示配置变化数量。

## 七、格式兼容性预检

因为四种格式共用同一集合，先检查节点是否能被四种格式同时表达。任一格式不支持时，节点统一排除，不进入 `output`。

记录：

- `compatibility_excluded_count`；
- `unsupported_json.count/reasons/nodes`；
- 节点 `status=unsupported`；
- 页面“格式不兼容”及逐格式原因。

常见原因包括 Loon 不支持某协议/传输/加密、sing-box 无 SSR outbound、端点或连接配置缺失等。排除是明确记录的不支持，不是伪造转换，也不是某格式静默少节点。

## 八、四格式实现

| 格式 | 实现 | 结构 | 校验 |
| --- | --- | --- | --- |
| Clash / Mihomo | `parser.clash_proxy` + 统一补全 | `proxies`、`proxy-groups`、`rules` | YAML 可解析、数量与名称集合一致 |
| sing-box | `parser.singbox_outbound` + 统一 TLS/传输补全 | `log/dns/inbounds/outbounds/route` | JSON 可解析、节点 outbound 数量与 tag 一致 |
| Base64 | `parser.to_uri` 生成链接后 Base64 | 每行一个节点 URI | 行数一致、片段名称解码一致 |
| Loon | 复用 `builder.build_loon` | Loon URI 文本 | 非注释行数一致、URI 协议前缀合法 |

四格式在生成时共同使用同一批冻结连接配置、同一节点集合、同一展示名称和同一顺序。格式切换与历史预览只读取本批已保存内容，不重新读取当前 P1。每个格式独立记录状态、字节、SHA256 和失败原因。

## 九、状态与失败

节点：

- `allowed`：通过过滤且格式兼容；
- `filtered`：关键词命中；
- `unsupported`：格式不兼容或当前连接配置不可用。

批次：

- `success`：输出非空，四格式均成功；
- `partial`：至少一个格式失败，另有成功格式；
- `failed`：四格式全部失败；
- `empty`：允许候选为空且四格式成功生成空结构；
- `stale`：页面派生状态，批次绑定的 P6.1 版本、P6.2.1 修订号或连接配置已不是当前值。

格式失败必须写真实 `failure_reason`，内容不写入伪造节点；下载失败格式返回错误。

`id,batch_no,created_at,trigger,p6_version_id,p6_version_no,p621_revision,p621_computed_at,category_counts_json,merged_count,unique_count,duplicate_count,filtered_count,candidate_count,compatibility_excluded_count,output_count,gpt_count,yt_count,tg_count,gh_count,multi_label_count,is_empty,status,status_reason,unsupported_json,node_set_sha256,config_sha256,config_node_count`

批次号 `P6.2.2-0001` 递增。

### 10.2 `np622_outputs`

`id,batch_id,format,status,node_count,generated_at,p6_version_id,p6_version_no,p621_revision,content_sha256,content_bytes,content_text,failure_reason`

唯一键 `(batch_id, format)`；每批四行，状态独立。内容是生成时冻结结果。

### 10.3 `np622_nodes`

`batch_id,node_id,node_name,airport_id,airport_name,server,port,protocol,speed_grade,display_name,labels_json,categories_json,status,hits_json,unsupported_json,score,p80_ms,params_json,config_sha256`

主键 `(batch_id, node_id)`；保存批次时点的完整连接配置，后续源数据变化不覆盖历史。

### 10.4 `np622_events`

`id,at,event,batch_id,detail_json`；记录批次生成事件，不写连接参数。

## 十一、API

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| GET | `/api/unified-subscription/summary` | 概况、当前合并结果、批次、四格式、节点、stale 原因 |
| GET | `/api/unified-subscription/history?limit=` | 追加式批次历史、逐批 stale 与配置变化数 |

格式键：`clash,singbox,base64,loon`。

下载响应带 `Content-Disposition: attachment`、`X-NodePoolME-Batch`、`X-NodePoolME-Nodes`、`Cache-Control: no-store`。

## 十二、历史与安全边界

- 每次生成新批次，绝不覆盖旧批次、旧输出或旧连接配置快照。
- 四格式同批关联，可查看对应 P6.1 版本、规则修订、配置总指纹、格式、数量和生成时间。
- 重复生成不触发 P2/P3/P4/P5，不创建 P6.1 版本。
- 旧批次在版本、规则或连接配置变化后只标记 `stale`，不自动删除；仍可追溯内容，但不能下载为当前订阅。
- 普通节点列表、批次列表、历史、Dashboard 和事件日志不返回 `params_json`，不展示密码、UUID、Reality 私钥类参数。
- 订阅文件本身包含客户端连接所需参数；下载继续受登录保护，未开放公网订阅或客户端正式拉取入口。
- 批次不保存机场原始订阅 URL 或上游凭据。

## 十三、页面与统计映射

页面总菜单 14 项，统一订阅为第 11 项，路由 `/unified-subscription`：

- 概况四联：合并记录、稳定 ID、过滤、输出；
- 顶部条：当前 P6.1、规则修订、最近生成、批次、节点集合 SHA、连接配置 SHA；
- 六类卡：standard/gpt/youtube/telegram/github/global；
- 标签卡：GPT/YT/TG/GH/多标签；
- 格式卡：四格式 tab、状态、数量、时间、P6.1/规则、SHA、内容、下载；
- 节点表：允许、过滤、不兼容三种状态，显示单节点配置指纹，不显示连接参数；
- 批次表：每批四格式独立状态与 stale 原因。

Dashboard `unified_subscription` 字段：

`status,nodes,filtered,labels{gpt,yt,tg,gh},last_generated,stale,stale_code,stale_reason,config_changed_count,config_missing_count,p6_version_no,revision,formats{clash,singbox,base64,loon}`

全部来自数据库当前批次与当前 P1 配置比对结果。
