## 一、交付范围

P3 在 P1 原始节点池与 P2 基础健康之上，增加五类业务能力的独立检测与独立资格管理。业务资格只回答“这个节点能否访问该业务”，不代表节点已成为优选节点。

实际交付包括：

1. 独立模块 `backend/business/`：业务目标、检测记录、Success/Failure/Unknown 归因、资格状态机、独立队列、汇总与设置。
2. 新增 7 张 `np3_*` 旁路表，不修改冻结的 17 张基线业务表，不写入 P1 的 `np_node_qualifications`。
3. 11 个 `/api/business/*` 接口，均要求登录。
4. 后台页面 `/business`「业务专项检测」，侧栏第 6 项，桌面表格与移动端卡片双布局。
5. Dashboard 增加 P3 业务统计面板：五类有资格节点数、待确认、Unknown、当前队列。
6. APScheduler 新增 `p3_business` 调度，10 秒 tick，按节点×业务入队，全局并发上限。
7. 自动化测试 `tests/test_p3_business.py` 12 项，覆盖独立业务、状态机、Unknown、目标故障、过期、队列唯一、配置失效、P1/P2 只读和 API。

新增表：

| 表 | 用途 |
| --- | --- |
| `np3_targets` | 五类业务各自唯一目标、期望状态码、周期、配置版本 |
| `np3_target_checks` | 目标自身可用性测试历史 |
| `np3_state` | 节点×业务当前状态、连续成功/失败、最近有效时间、下次检测 |
| `np3_checks` | 每次节点业务检测的完整结果、HTTP 状态、耗时、失败原因 |

## 三、检测目标与配置说明

### 1. 目标管理

- 后台可修改名称、URL、期望状态码（如 `200-399` 或 `200,204,301`）、单业务周期（0 跟随全局或 15–1440 分钟）和启用状态。
- 支持单业务手动测试、启停和恢复五类默认目标。
- 每类业务固定一个目标，不提供任意新增业务，避免偏离五类固定范围。
- 名称修改不提升配置版本，不失效历史。
- URL、期望状态码、启用状态或单业务周期变化会提升该目标 `config_version`，只清空该业务的状态、连续计数、资格和队列，并将在途检查标为 `config_changed`；其他四类业务不受影响。

### 2. 全局设置

| 设置 | 默认 | 范围 | 说明 |
| --- | --- | --- | --- |
| `p3_interval_minutes` | 360 分钟 | 30–1440 | 全局业务检测周期 |
| `p3_valid_hours` | 24 小时 | 1–72 | 检测结果有效期 |
| `p3_concurrency` | 10 | 1–50 | 统一并发上限，按业务任务计数 |
| 首次复查 | 15 秒 | 固定 | 第 1 次有效失败后 |
| 第二次复查 | 30 秒 | 固定 | 第 2 次有效失败后 |
| 挂起/Unknown 复查 | 5 分钟 | 固定 | 待确认、暂停资格、Unknown |

### 3. 真实 HTTPS 路径

每次节点业务检测严格走节点自己的 Mihomo 每节点 SOCKS listener：

1. 控制端先对目标做一次独立 selftest；selftest 不可用时，本轮该目标对所有节点返回 Unknown，不探测节点。
2. 节点侧通过 `probe_target(target, proxy_port=<该节点端口>)` 执行 DNS → TCP → TLS → HTTPS。
3. 只有 HTTPS 阶段真实执行并得到期望状态码，才判定 Success。
4. 仅 DNS 成功、仅 TCP 连接成功、仅 TLS 握手成功都不能获得业务资格。
5. 节点名称、机场名称、地区标签、协议类型不参与任何判定；分类函数只读取 HTTPS 阶段、TLS/TCP 阶段和失败原因。

## 四、Success、Failure、Unknown 判定

| 场景 | 分类 | 连续计数 | 对已有资格 |
| --- | --- | --- | --- |
| HTTPS 执行成功且状态码在期望范围 | Success | 成功 +1，失败清零 | 保持或按规则获得 |
| HTTPS 执行但状态码不在期望范围 | Failure | 失败 +1，成功清零 | 前两次保留，第三次暂停 |
| TCP 五次全部失败 | Failure | 失败 +1 | 同上 |
| TLS 握手失败 | Failure | 失败 +1 | 同上 |
| 目标 selftest 不可用 | Unknown | 不计数 | 保留 |
| DNS 超时或责任不明 | Unknown | 不计数 | 保留 |
| 代理内核未就绪 | Unknown | 不计数 | 保留 |
| 检测批次异常或任务中断 | Unknown / 队列释放 | 不计数 | 保留 |
| 目标配置变更后的在途结果 | 丢弃 | 不计数 | 只影响对应业务 |

Unknown 不累计连续失败，不撤销已有资格，也不覆盖之前的有效检测结论。目标故障、检测服务异常、责任不明的超时与中断统一归 Unknown。

## 五、资格状态机

状态：`untested` 未检测、`unknown` Unknown、`pending` 待确认、`qualified` 已获得资格、`suspended` 暂停资格。

| 当前状态 | 事件 | 下一状态 | 下次检测 |
| --- | --- | --- | --- |
| 未检测 / Unknown / 待确认 | 有效成功第 1 次 | 待确认 | 5 分钟 |
| 未检测 / Unknown / 待确认 / 暂停 | 有效成功第 2 次 | 已获得资格 | 按业务周期，且不越过有效期 |
| 已获得资格 | 有效成功 | 已获得资格 | 按业务周期 |
| 任意非暂停 | 有效失败第 1 次 | 待确认 | 15 秒 |
| 待确认 | 有效失败第 2 次 | 待确认 | 30 秒 |
| 待确认 / 已获得资格 | 有效失败第 3 次 | 暂停资格 | 5 分钟 |
| 已获得资格 | 有效失败第 1/2 次 | 已获得资格 | 15/30 秒 |
| 任意 | Unknown | 保持原状态；未检测/Unknown 记为 Unknown | 5 分钟 |
| 已获得资格 | 结果过期 | 保留资格历史，但 `qualification_active=false` | 立即到期重检 |

资格变化写入 `np3_events`：`qualification_granted`、`qualification_suspended`、`qualification_recovered`、`business_unknown`、`check_discarded`。连续成功 2 次获得资格；连续失败 3 次暂停；恢复后连续成功 2 次写 `qualification_recovered`。

有效期按 `last_valid_at + p3_valid_hours` 计算。过期数据必须重检，但过期不等于业务失败：不增加失败计数，不清空资格历史，也不计入 Dashboard “当前有资格节点数”。

## 六、调度与队列

- `job_business_p3` 每 10 秒 tick，`max_instances=1`、`coalesce=True`，启动后约 20 秒首跑。
- 每个队列单位是“节点 × 业务”，不是“节点”；某业务探测失败不会阻塞同一节点的其他业务。
- `uq_np3_queue_active` 部分唯一索引保证同一节点同一业务最多一个 pending/running。
- 不同业务可独立到期、独立入队、独立并发；统一受 `p3_concurrency` 约束。
- 批次按预留的队列任务执行；`_run_batch` 外层异常会把未完成队列行标为 `error`，并把运行中检查标为 Unknown，释放并发资源。
- 启动时 `startup_reset` 回收上次异常退出遗留的队列。
- 自动检测与手动检测共用同一队列和唯一约束；手动重复检测不会重复排队。

## 七、P1 / P2 联动

| 约束 | 实现 |
| --- | --- |
| 检测对象来自 P1 原始节点池 | `np_nodes WHERE source_active=1`，不是仅健康池 |
| 新节点、观察节点、健康节点均可检测 | P3 不按 `management_layer` 过滤 |
| 不健康节点保留历史但不获得正式优选 | 业务资格独立保存，不改 P1 管理层和竞争轴 |
| P3 不改 P2 基础健康 | 不写 `np_nodes.base_health`、`np2_node_state` |
| P3 不改 P1 竞争状态 | 不写 `competition_state`、`np_node_qualifications` |
| 页面可读 P1/P2 字段 | 节点详情只读展示 P2 基础健康、管理层和竞争状态 |

专项测试在批次执行前后对比 `np_nodes.base_health`、`management_layer`、`competition_state`，确认完全不变。

## 八、后台页面与 Dashboard

### `/business` 页面

- 五类业务独立统计卡：有资格节点数、待确认、Unknown、目标启停。
- 全局补充统计：五类合计有资格、待确认节点、Unknown 节点、检测队列（排队/执行）。
- 五个目标卡：URL、期望状态、单业务周期、配置版本、最近测试状态；支持启停、测试、编辑、恢复默认。
- 节点表：五列业务状态、连续成功/失败、是否检测中、资格数、最近检测；支持按业务和资格状态筛选。
- 节点详情抽屉：五类业务各自独立的连续成功、连续失败、最近有效、有效期至、最近检测、下次检测、HTTP 状态、耗时、阶段结果、最近 5 条检测和资格事件。
- 移动端为节点卡片与双列业务格，详情抽屉可滚动阅读，不把五类合并成一个总状态。
- 手动检测支持单节点五项、单节点指定业务、全部节点五项。

### Dashboard

新增“业务专项检测 · P3”面板，显示五类有资格节点数、待确认节点、Unknown 节点、当前检测队列和 P2 健康参考；数据来自 `/api/business/summary` 实时查询，不使用固定演示数字。

## 十一、边界与遗留

本阶段未实施：P4 七天质量评分与下载速度、P5 智能竞争、P6 过滤发布、P7 决策历史。

需要项目负责人确认的取舍：

1. 配置变更即清空对应业务全部节点结论和资格。这是为保证新目标不被旧结论污染；代价是该业务短期回到未检测。
2. 过期资格保留历史但当前不计为有资格；Dashboard 只统计当前有效资格。
3. 五类业务固定，不允许后台新增第六类；目标地址可改，业务范围不可扩。
4. 当前云主机出口对 GPT/YouTube/Telegram 目标不可达，只验证了“目标故障归 Unknown”的代码路径；节点代理出口的真实五类访问需在具备 Mihomo 的部署网络复核。
5. P3 按需求只保存 DNS/TCP/TLS/HTTPS 阶段，不保存 P2 那样的 TCP 五次原始样本；业务判定不依赖 P2 延迟等级。

P3 完成后停止，等待项目负责人验收，不进入 P4。
