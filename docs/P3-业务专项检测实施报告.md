## 三、检测目标与配置说明

### 1. 目标管理

- 后台可修改名称、URL、期望状态码（如 `200-399` 或 `200,204,301`）、单业务周期（0 跟随全局或 15–1440 分钟）和启用状态。
- 支持目标启停、编辑和恢复五类默认目标；不提供服务器直连目标的手动“测试”入口。
- 每类业务固定一个目标，不提供任意新增业务，避免偏离五类固定范围。
- 名称修改不提升配置版本，不失效历史。
- URL、期望状态码、启用状态或单业务周期变化会提升该目标 `config_version`，只清空该业务的状态、连续计数、资格和队列，并将在途检查标为 `config_changed`；其他四类业务不受影响。

### 2. 全局设置

| 设置 | 默认 | 范围 | 说明 |
| --- | --- | --- | --- |
| `p3_interval_minutes` | 360 分钟 | 30–1440 | 全局业务检测周期 |
| `p3_valid_hours` | 24 小时 | 1–72 | 检测结果有效期 |
| `p3_concurrency` | 10 | 1–50 | 统一并发上限，按业务任务计数 |
| 首次复查 | 15 秒 | 固定 | 第 1 次有效失败后 |
| 第二次复查 | 30 秒 | 固定 | 第 2 次有效失败后 |
| 挂起/Unknown 复查 | 5 分钟 | 固定 | 待确认、暂停资格、Unknown |

### 3. 节点 DNS 与异常归因（v2.038 修正）

P3 的 DNS 阶段必须描述被测节点出口，不得使用控制端本机解析。规则固定为：

1. `backend/business/service.py::node_probe` 固定调用 `prober.probe_target(..., proxy_dns=True)`，所有 P3 业务任务都启用节点 DNS 模式。
2. 节点 DNS 由 `_proxy_dns()` 通过同一节点的 SOCKS5 listener、以域名 ATYP=0x03 发起 CONNECT 确认；不调用 `_dns()` 或控制端 `getaddrinfo()` 解析目标域名，也不把控制端解析出的 IP 交给代理。
3. SOCKS5 没有“只解析、不连接”的命令，因此使用一个独立的域名 CONNECT 作为节点解析见证。只有 CONNECT 成功（reply 0x00）才确认节点侧解析并连通；连接被拒绝（0x05）可能是代理策略在解析前直接拒绝，不能证明 DNS 成功，记 Unknown `proxy_dns_target_refused`。
4. DNS 阶段独立保存 latency、`resolver=node_proxy`、`via=socks5_domain`、reply 和失败原因；DNS 成功后才进入 TCP。
5. DNS、TCP、TLS、HTTPS 共用同一个 `proxy_port`；TCP/TLS 使用原始 hostname，不使用控制端解析出的 IP。
6. 节点 DNS 的 host unreachable、SOCKS 协议异常、代理端口不可用、超时、检测器异常均记 Unknown；无法确认解析成功时不伪造 Success 或 Failure。
7. TLS 真正握手超时或 `ssl.SSLError` 记 Failure；代理端口未就绪、SOCKS 协议错误、检测器内部异常、任务中断记 Unknown。不会为了降低 Failure 数量而把所有 TLS 异常改为 Unknown。
8. P2 默认 `proxy_dns=False`，保留其控制端 DNS 行为；只有 P3 节点探测启用节点 DNS 模式。

### 4. 代理专用目标判定规则（v2.037 修正）

P3 的五类目标均属于必须经被测节点出口访问的业务目标，因此检测目标状态时不再从控制端直接访问目标。规则固定为：

1. 取消服务器对业务目标的直连可用性检查，不要求独立判断目标在服务器侧是否可达。
2. 每个节点×业务任务都直接进入该节点的检测，不再等待或依赖服务器侧目标检查。
3. 所有业务检测请求只经当前被测节点的 Mihomo 每节点 SOCKS listener 发出，使用 `probe_target(target, proxy_port=<该节点端口>, proxy_dns=True)`；DNS 也在该出口完成。
4. 节点访问失败时，按本次 DNS/TCP/TLS/HTTPS 实际阶段结果归因为 Failure 或 Unknown；服务器无法直连目标不构成目标故障，也不影响节点检测。
5. DNS → TCP → TLS → HTTPS 的阶段依赖保持不变：前一阶段未成功，后续阶段不执行；P3 的 DNS 由节点代理完成，仅 HTTPS 真实执行并命中期望状态码才 Success。
6. 不随机选择其他节点代替被测节点，不把任何“参考节点”的结果当作目标状态。
7. P3 不开发目标投票、参考节点或多节点交叉验证；目标是否可达只由每个被测节点自己的结果回答。
8. 目标配置管理保留：名称、URL、期望状态码、周期、启停、配置版本和恢复默认均可用；目标配置变更只失效对应业务，不触发服务器直连健康检查。
9. 不修改 P1、P2 已验收功能，不提前实施 P4–P7。

代码层不再存在控制端 `target_probe`、目标检查缓存或“目标不可用则整批 Unknown”的短路；`np3_target_checks` 仅作为 v2.036 历史表保留，不再新增记录。

## 四、Success、Failure、Unknown 判定

| 场景 | 分类 | 连续计数 | 对已有资格 |
| --- | --- | --- | --- |
| HTTPS 执行成功且状态码在期望范围 | Success | 成功 +1，失败清零 | 保持或按规则获得 |
| HTTPS 执行但状态码不在期望范围 | Failure | 失败 +1，成功清零 | 前两次保留，第三次暂停 |
| TCP 五次全部失败 | Failure | 失败 +1 | 同上 |
| 节点 DNS 代理域名解析成功 | Success | 成功 +1，失败清零 | 可继续 TCP |
| TLS 真正握手超时或 SSL 错误 | Failure | 失败 +1 | 同上 |
| 节点 DNS host unreachable、SOCKS 错误或超时 | Unknown | 不计数 | 保留 |
| 代理端口/内核未就绪、检测器异常、任务中断 | Unknown | 不计数 | 保留 |
| 检测批次异常或任务中断 | Unknown / 队列释放 | 不计数 | 保留 |
| 目标配置变更后的在途结果 | 丢弃 | 不计数 | 只影响对应业务 |

Unknown 不累计连续失败，不撤销已有资格，也不覆盖之前的有效检测结论。服务器直连目标失败不参与分类；代理端口未就绪、节点 DNS 责任不明、检测器异常、超时与中断统一归 Unknown。

## 五、资格状态机

状态：`untested` 未检测、`unknown` Unknown、`pending` 待确认、`qualified` 已获得资格、`suspended` 暂停资格。

| 当前状态 | 事件 | 下一状态 | 下次检测 |
| --- | --- | --- | --- |
| 未检测 / Unknown / 待确认 | 有效成功第 1 次 | 待确认 | 5 分钟 |
| 未检测 / Unknown / 待确认 / 暂停 | 有效成功第 2 次 | 已获得资格 | 按业务周期，且不越过有效期 |
| 已获得资格 | 有效成功 | 已获得资格 | 按业务周期 |
| 任意非暂停 | 有效失败第 1 次 | 待确认 | 15 秒 |
| 待确认 | 有效失败第 2 次 | 待确认 | 30 秒 |
| 待确认 / 已获得资格 | 有效失败第 3 次 | 暂停资格 | 5 分钟 |
| 已获得资格 | 有效失败第 1/2 次 | 已获得资格 | 15/30 秒 |
| 任意 | Unknown | 保持原状态；未检测/Unknown 记为 Unknown | 5 分钟 |
| 已获得资格 | 结果过期 | 保留资格历史，但 `qualification_active=false` | 立即到期重检 |

资格变化写入 `np3_events`：`qualification_granted`、`qualification_suspended`、`qualification_recovered`、`business_unknown`、`check_discarded`。连续成功 2 次获得资格；连续失败 3 次暂停；恢复后连续成功 2 次写 `qualification_recovered`。

有效期按 `last_valid_at + p3_valid_hours` 计算。过期数据必须重检，但过期不等于业务失败：不增加失败计数，不清空资格历史，也不计入 Dashboard “当前有资格节点数”。

## 六、调度与队列

- `job_business_p3` 每 10 秒 tick，`max_instances=1`、`coalesce=True`，启动后约 20 秒首跑。
- 每个队列单位是“节点 × 业务”，不是“节点”；某业务探测失败不会阻塞同一节点的其他业务。
- `uq_np3_queue_active` 部分唯一索引保证同一节点同一业务最多一个 pending/running。
- 不同业务可独立到期、独立入队、独立并发；统一受 `p3_concurrency` 约束。
- 批次按预留的队列任务执行；`_run_batch` 外层异常会把未完成队列行标为 `error`，并把运行中检查标为 Unknown，释放并发资源。
- 启动时 `startup_reset` 回收上次异常退出遗留的队列。
- 自动检测与手动检测共用同一队列和唯一约束；手动重复检测不会重复排队。

### 4. 节点 DNS 与同出口验证

v2.038 不再用控制端直连目标或控制端 DNS 的结果证明业务可用性。验证以节点探测为准：

| 验证 | 结果 | 证据 |
| --- | --- | --- |
| DNS 不用控制端本机解析 | 通过 | 测试让 `_dns` 抛错仍可完成节点 DNS；`_proxy_dns` 收到 `chatgpt.com` 的 SOCKS ATYP=3 域名请求 |

## 十一、边界与遗留

本阶段未实施：P4 七天质量评分与下载速度、P5 智能竞争、P6 过滤发布、P7 决策历史。

需要项目负责人确认的取舍：

1. 配置变更即清空对应业务全部节点结论和资格。这是为保证新目标不被旧结论污染；代价是该业务短期回到未检测。
2. 过期资格保留历史但当前不计为有资格；Dashboard 只统计当前有效资格。
3. 五类业务固定，不允许后台新增第六类；目标地址可改，业务范围不可扩。
4. 当前云主机没有可直接调用的 Mihomo 节点代理，未实测公网五类目标；已用本地 SOCKS5 模拟器验证节点 DNS 域名请求、同出口、Unknown/Failure 归因。具备 Mihomo 的部署网络仍需复核五类目标的真实节点侧结果。
5. P3 按需求只保存 DNS/TCP/TLS/HTTPS 阶段，不保存 P2 那样的 TCP 五次原始样本；业务判定不依赖 P2 延迟等级。

P3 完成后停止，等待项目负责人验收，不进入 P4。
