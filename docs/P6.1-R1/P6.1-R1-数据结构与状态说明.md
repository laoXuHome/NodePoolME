# NodePoolME P6.1-R1 数据结构与状态说明

## 一、总体原则

P6.1-R1 仍是 P5 下游的只读投影层：

- 读取 `np5_state` 中 `state='preferred'` 的节点；
- 读取 `np5_runs` 最近一轮状态，作为版本有效性门槛；
- 读取 `np_nodes`、`airports` 的节点名、机场、服务器、端口用于展示和身份判定；
- 只写 `np6_*` 旁路表；
- 不写 P1–P5 状态、评分、资格或历史。

## 二、类别

固定六类，键值与 P5 一致：

| 键 | 名称 |
|---|---|
| `standard` | 标准综合优选 |
| `gpt` | GPT 专项优选 |
| `youtube` | YouTube 专项优选 |
| `telegram` | Telegram 专项优选 |
| `github` | GitHub 专项优选 |
| `global` | 国外综合专项优选 |

## 三、身份签名（R1 核心变更）

### 1. 签名版本

`np6_versions.detail_json` 新增：

```json
{ "signature_version": 2 }
```

旧版本可能没有该字段，按版本 1 处理。

### 2. 签名输入

每个节点按类别分桶，身份数组为：

```json
[
  "node_id",
  "node_name",
  "airport_id",
  "airport_name",
  "server",
  "port"
]
```

六类各自按 `node_id` 排序后序列化：

```json
{
  "signature_version": 2,
  "categories": {
    "standard": [["node_id", "name", "airport_id", "airport_name", "server", "port"]],
    "gpt": [],
    "youtube": [],
    "telegram": [],
    "github": [],
    "global": []
  }
}
```

对上述 JSON 计算 SHA-256，写入 `np6_versions.signature`。

### 3. 不进入签名的字段

以下字段变化不生成新版本，避免噪声：

- 竞争分数 `score`；
- 成熟度 `maturity`；
- TCP P80 `p80_ms`；
- 延迟等级、速度等级、下载速度；
- P5 原因码、优选起点；
- 仅 P5 run 编号变化但优选成员与身份完全一致。

### 4. 有效信息变化

以下任一变化生成新的有效版本：

| 字段 | 说明 |
|---|---|
| `category` | 节点进入或退出类别；跨类按新增/移除记录 |
| `node_id` | 节点身份变化；旧 ID 移除、新 ID 新增 |
| `node_name` | 最终展示名称变化；同类别同 ID 记为保留并标注 |
| `airport_id` | 机场 ID 变化；同类别同 ID 记为保留并标注 |
| `airport_name` | 机场显示名变化；同类别同 ID 记为保留并标注 |
| `server` | 服务器地址变化；同类别同 ID 记为保留并标注 |
| `port` | 端口变化；同类别同 ID 记为保留并标注 |

## 四、表结构

### 1. `np6_versions`

版本头，只追加。关键字段：

| 字段 | 说明 |
|---|---|
| `id` | 内部版本 ID |
| `version_no` | `P6.1-0001` |
| `created_at` | 生成时间 |
| `trigger` | `manual` / `auto` / `startup` / `cli` |
| `valid` | 有效状态 |
| `is_empty` | 是否有效空版本 |
| `total_nodes` | 六类条目总量，同节点跨类重复计数 |
| `category_counts_json` | 六类数量 |
| `change_counts_json` | 六类新增/移除/保留数量 |
| `previous_version_id` / `previous_version_no` | 上一有效版本 |
| `source_run_id` / `source_run_at` | 来源 P5 轮次 |
| `signature` | R1 身份签名 |
| `detail_json` | 汇总信息 + `signature_version` |

### 2. `np6_entries`

版本内六类完整节点，也是内部待定订阅池。

关键字段：

| 字段 | 说明 |
|---|---|
| `version_id` | 所属版本 |
| `category` | 六类之一 |
| `node_id` | P1 节点 ID |
| `node_name` | 写入时节点名称 |
| `airport_id` / `airport_name` | 写入时机场信息 |
| `server` / `port` | 写入时服务地址 |
| `score` / `maturity` / `p80_ms` | 写入时竞争证据 |
| `delay_grade` / `speed_grade` / `speed_mb_s` | 写入时评价 |
| `preferred_since` / `last_reason` | P5 优选起点与原因 |
| `detail_json` | P5 附加详情 |

主键：`(version_id, category, node_id)`。同一节点允许出现在不同类别。

### 3. `np6_changes`

版本差异流水。`detail_json` 在 R1 后为：

```json
{
  "before": { "...": "变化前完整条目" },
  "after":  { "...": "变化后完整条目" },
  "changed_fields": [
    {
      "field": "node_name",
      "label": "节点名称",
      "before": "旧名",
      "after": "新名"
    }
  ]
}
```

规则：

| 变化类型 | `before` | `after` | `changed_fields` |
|---|---|---|---|
| `added` | `null` | 新条目 | `[]` |
| `removed` | 旧条目 | `null` | `[]` |
| `retained` 无身份变化 | 旧条目 | 新条目 | `[]` |
| `retained` 有身份变化 | 旧条目 | 新条目 | 字段、旧值、新值 |

每条变化仍有 `category`、`node_id`、`change_type`、`at`、`trigger`，可按类别追溯。

### 4. `np6_events`

记录 `snapshot_created`、`snapshot_unchanged`、`snapshot_rejected`，包含时间、版本和原因。

## 五、版本生成状态机

```text
无 P5 轮次                  -> 拒绝（no_p5_run）        -> 保留上一有效版本
P5 running / partial        -> 拒绝（run_not_success）   -> 保留上一有效版本
P5 success + 身份签名相同    -> unchanged，不生成版本
P5 success + 身份签名不同    -> 生成新版本
P5 success + 无 preferred   -> 生成有效空版本（is_empty=1）
```

### 旧版本兼容

```text
最新版本 detail 无 signature_version
  -> 当前条目身份 == 旧版本 np6_entries 身份：unchanged，不建版本
  -> 当前条目身份 != 旧版本 np6_entries 身份：生成新版本

最新版本 detail signature_version >= 2
  -> 直接比较 R1 签名
```

此规则保证 v2.044 升级到 v2.045 时，不会因签名算法变化凭空生成重复版本。

## 六、只读查询语义

- `GET /api/final/*` 不生成版本。
- 刷新页面、重复请求、切换分类、打开历史版本均不改变 `np6_versions`。
- `GET /api/final/diff` 返回变化项时，`before`、`after`、`changed_fields` 位于顶层，页面无需解析嵌套 `detail_json`。
- 历史差异读取 `np6_changes`，不重新计算当前 P5，不会随 P5 后续变化漂移。
- `POST /api/final/snapshot` 是唯一生成入口。

## 七、接口响应要点

`GET /api/final/diff` 的保留节点变化项示例：

```json
{
  "category": "standard",
  "node_id": 12,
  "change_type": "retained",
  "node_name": "新名称",
  "airport_name": "新机场",
  "before": {
    "node_name": "旧名称",
    "airport_id": 1,
    "airport_name": "旧机场",
    "server": "1.1.1.1",
    "port": 443
  },
  "after": {
    "node_name": "新名称",
    "airport_id": 2,
    "airport_name": "新机场",
    "server": "1.1.1.1",
    "port": 443
  },
  "changed_fields": [
    {"field": "node_name", "label": "节点名称", "before": "旧名称", "after": "新名称"},
    {"field": "airport_id", "label": "机场 ID", "before": 1, "after": 2},
    {"field": "airport_name", "label": "机场名称", "before": "旧机场", "after": "新机场"}
  ]
}
```

## 八、与后续阶段的数据边界

- 待定订阅池 = 当前版本 `np6_entries`，不是健康池，不是发布订阅。
- 后续关键词过滤只能作用于下发出口，不得修改 `np6_entries` 或历史快照。
- P6.1-R1 不创建订阅表、不写订阅文件、不暴露客户端拉取路由。
